## I. Overall requirements
### 1. Product overview
Arena3 is one web application that runs a single sports centre in Ho Chi Minh City, from court booking to the end-of-day till. It serves badminton, basketball and volleyball courts, membership plans, coached classes and the front desk.
| Portal | Route | Who uses it | Main purpose |
| Public site | `/`, `/login`, `/register` | Guest | Browse prices and classes, sign up, sign in |
| Member portal | `/app` | Member | Book courts, pay, enrol in classes, show the gate pass |
| Front desk | `/desk` | Receptionist | Serve walk-ins, take payments, run the gate and the till |
| Coach portal | `/coach` | Coach | Teach classes, take attendance, track student progress |
| Manager portal | `/manager` | Manager | Set prices and rules, staff the centre, read reports |
The app is built with TanStack Start and React, with a JSON API under `/v1` in the same deployment. Production runs on Vercel with Neon PostgreSQL. Development runs offline on an embedded PGLite database that migrates and seeds itself.
**Out of scope.** Multi-branch operation, payroll, native mobile apps and SMS delivery are not part of this release. Class fees are covered by membership plans and are not charged per session.

### 3. Main workflows
Four activity diagrams cover the workflows that move money or change a schedule. Each uses swimlanes, one initial node, guarded decisions and one final node.
#### 3.1 Register a member account
A guest becomes a member only after proving the email address with a one-time code.
&#91;image: Figure 2 — Activity diagram: Register a member account\]
The code expires after 5 minutes. Too many wrong attempts lock the challenge for 15 minutes. A successful check creates the account, writes an audit entry and signs the member in.
#### 3.2 Book a court and pay
A booking is confirmed only when money is known to have arrived or plan hours are spent.
&#91;image: Figure 3 — Activity diagram: Book a court and pay\]
A slot is held for 5 minutes while the member pays. Three paths follow:
- **payOS QR:** the booking is confirmed only after Arena3 verifies payOS's signed result and the amount.
- **Bank transfer:** the hold stretches to 120 minutes and the transfer waits for the front desk to reconcile it.
- **Plan quota:** one court hour is taken from the member's active plan.
#### 3.3 Enrol in a class or join the waitlist
A full class never refuses a member outright; it offers a waitlist place instead.
&#91;image: Figure 4 — Activity diagram: Enrol in a class or join the waitlist\]
When a seat frees up, the next member gets a 2-hour offer. The scheduled job expires an unanswered offer and moves on to the next member.
#### 3.4 Refund a payment
A large refund needs a second person, so no receptionist can refund their own sale above the limit.
&#91;image: Figure 5 — Activity diagram: Refund a payment\]
Refunds up to 1,000,000đ post at once. Larger refunds wait for a manager, who approves or rejects them. Both outcomes are audited and the member is notified.

#### 1.4 Non-screen functions
Ten background jobs keep holds, bookings, plans and messages correct without anyone pressing a button. A single probe query checks every 15 seconds whether any job has work.
| # | Function | Trigger | Description |
| 1 | Expire holds | Every 15 s, when due | Cancels court holds past their hold time and frees the court. |
| 2 | Mark no-shows | Every 15 s, when due | Marks a confirmed booking as a no-show 10 minutes after its start without check-in. |
| 3 | Complete bookings | Every 15 s, when due | Closes an in-use booking 10 minutes after it ends. |
| 4 | Send notifications | Every 15 s, when due | Sends up to 50 queued messages. A message is marked sent only on delivery and stops after 5 tries. |
| 5 | Withdraw payment links | Every 15 s, when due | Cancels a payOS link whose court hold has lapsed. Runs only when payOS is configured. |
| 6 | Expire waitlist offers | Every 15 s, when due | Expires an unanswered offer and offers the seat to the next member. |
| 7 | Lock attendance | Every 15 s, when due | Closes a session's register 2 hours after it ends. |
| 8 | Expire plans | Every 15 s, when due | Marks a plan expired the day after its end date. |
| 9 | Plan expiry reminders | Every 15 s, when due | Sends one in-app reminder 7 days, 3 days and 0 days before a plan ends. |
| 10 | Generate sessions | Every 10 minutes | Creates upcoming sessions for every open class. |
| 11 | payOS webhook | Called by payOS | Verifies the signature and amount, then posts the payment through the normal settle path. |
The job loop starts with the first API request on each server instance. Each job with work runs in its own transaction, so one failure cannot roll back another.

### 2. Use case specifications
This section specifies all 44 use cases in the FPT template: a header table, then the normal flow, the alternative flows and the exceptions. Each alternative or exception is numbered by the step it branches from, so 3a branches from step 3.
Every refusal named below reaches the screen as a sentence, with its error code and, where a business rule applies, the rule code from V.1. The common requirements in V.3 (idempotency keys, audit rows, sessions and rate limits) apply to every use case and are not repeated.
#### 2.1 UC-01 Browse courts, classes and prices
| Field | Detail |
| UC ID and name | UC-01 Browse courts, classes and prices |
| Created by / date | Arena3 team / 2026-10-12 |
| Primary actor | Guest |
| Secondary actors | None |
| Trigger | The guest opens the public site (/). |
| Description | A guest reads the sports, courts, opening hours, plan prices and open classes before deciding to join. |

**Normal flow**
1. The guest opens the landing page.
2. The system shows the sports, the opening hours, the court list and the plan prices.

**Exceptions**

#### 2.2 UC-02 Register a member account
| Field | Detail |
| UC ID and name | UC-02 Register a member account |
| Created by / date | Arena3 team / 2026-10-12 |
| Primary actor | Guest |
| Secondary actors | Email service (SMTP) |
| Trigger | The guest selects Create an account on /register. |
| Description | A guest creates a member account and proves the email address with a one-time code. |
| Preconditions | The guest is signed out. The phone and email have no account yet. |
| Postconditions | A member account exists, the guest is signed in for seven days, and an audit row is written. |
| Priority | Must have |
| Frequency of use | Once per new member |
| Business rules | BR-01, BR-02, BR-03, BR-04 |
**Normal flow**
1. The guest enters full name, phone, email, password and date of birth.
2. The guest accepts the terms and the data-privacy notice, then submits.
3. The system checks every field and confirms the phone and email are unused.
4. The system stores a sign-up challenge for five minutes and emails a one-time code.
5. The guest enters the code on the same page.
6. The system checks the code, creates the member account and returns a session token.
7. The system opens My schedule.
**Alternative flows**
- 1a. The guest is under 16: the guest also enters a guardian's name and phone (BR-03).
**Exceptions**
- 3a. A field is malformed: VALIDATION, and the field to correct is marked.
- 3b. The phone or email already has an account: BR-01.
- 3c. The password is shorter than 8 characters or lacks letters and digits: BR-02.
- 3d. The terms are not accepted: BR-04.
- 6a. The code is wrong: the attempt is counted and the guest may try again.
- 6b. The code is older than five minutes: the guest submits the form again to receive a new code.
- 6c. Five wrong attempts: the challenge is locked for 15 minutes (RATE\_LIMITED).

#### 2.3 UC-03 Sign in and sign out
| Field | Detail |
| UC ID and name | UC-03 Sign in and sign out |
| Created by / date | Arena3 team / 2026-10-12 |
| Primary actor | Registered User |
| Secondary actors | None |
| Trigger | The user selects Sign in on /login, or Sign out in any portal. |
| Description | A registered user opens a session with phone or email and password, and closes it when done. |
| Preconditions | The user has an active account. |
| Postconditions | Sign in: a session token is stored as a hash and the user lands on the home screen of their role. Sign out: the session is revoked. |
| Priority | Must have |
| Frequency of use | Many times a day |
| Business rules | None |
**Normal flow**
1. The user enters a phone or email and the password.
2. The system checks the password against the stored salted hash.
3. The system creates a session: seven days for a member, twelve hours for staff.
4. The system opens the portal for the user's role: /app, /desk, /coach or /manager.
5. Later, the user selects Sign out.
6. The system revokes the session and opens the landing page.
**Alternative flows**
- 4a. The user opened a protected page before signing in: the system returns the user to that page.
**Exceptions**
- 2a. The password is wrong: UNAUTHENTICATED, and the attempt is counted.
- 2b. Five wrong passwords: sign-in is locked for 15 minutes (RATE\_LIMITED).
- 2c. The account is locked or disabled: FORBIDDEN, and the user is told to contact the centre.
#### 2.4 UC-04 Reset a forgotten password
| Field | Detail |
| UC ID and name | UC-04 Reset a forgotten password |
| Created by / date | Arena3 team / 2026-10-12 |
| Primary actor | Registered User |
| Secondary actors | Email service (SMTP) |
| Trigger | The user selects Forgot password on /login. |
| Description | A user who has forgotten the password proves control of the account email with a one-time code and sets a new password. |
| Preconditions | The user is signed out. |
| Postconditions | The password is replaced, every other session of the user is revoked, and an audit row is written. |
| Priority | Must have |
| Frequency of use | A few times a week |
| Business rules | BR-02 |
**Normal flow**
1. The user enters the phone number of the account on /forgot.
2. The system emails a one-time code valid for five minutes to the address on the account.
3. The user enters the code and a new password twice.
4. The system checks the code and the password rules.
5. The system stores the new password and signs the user in.
**Exceptions**
- 2a. The phone has no account: the system shows the same message as for a real account, so it never reveals who is a member.

## IV. Non-functional requirements
Arena 3 must keep money and schedules correct under concurrency, respond quickly on a phone, and protect member data. This section names the external interfaces and the quality attributes that make this so.
### 1. External interfaces
#### 1.1 User interfaces
Arena 3 is one responsive web application with four portals, and every screen works from a 375 px phone width.
- The interface is available in English and Vietnamese, and the user switches language in the header.
- Running text uses Be Vietnam Pro, which renders Vietnamese diacritics correctly. Headings use Newsreader and figures use Anton.
- Amounts are written in VND with a lowercase đ, for example 1,500,000đ.
- A refusal is shown as a sentence that says what to do instead. The error code travels with it for support.
- Motion is decorative only, and no action is discoverable only through animation.
#### 1.2 Software interfaces
The application talks to five outside systems, and each has a defined fallback.
| Interface | Purpose | Protocol and data | Failure behaviour |
| Arena 3 API (`/v1`) | Every screen reads and writes through it | JSON over HTTPS with a bearer token; served inside the web app | Errors return `{ code, message }`, plus `field` or `br` where one applies |
| payOS | Payment links, VietQR codes, link status and payment webhooks | HTTPS REST; the webhook is signed with the checksum key | A payment posts only when payOS confirms it, and the amount must equal the amount due |
| Google Gemini (`gemini-2.5-flash`) | Answers in the AI assistant | HTTPS; the prompt carries centre data only, never member data | 12-second timeout, then xAI Grok, then rule-based answers |
| Email (SMTP through nodemailer) | One-time codes and notifications | SMTP with the centre's sender address | Codes are sent at once; notifications are queued and retried up to five times |
| PostgreSQL 16 | All records | Neon in production; embedded PGLite when no `DATABASE_URL` is set | Schema changes are forward-only numbered migrations, each run in one transaction |
The application is hosted on Vercel. Background jobs start with the first API request and run in a loop every 15 seconds.
#### 1.3 API error codes
Every API error uses one of these codes, so a screen can react to the code rather than parse the text.
| HTTP | Code | Meaning |
| 400 | `VALIDATION` | A value is malformed; `field` names the input to correct |
| 401 | `UNAUTHENTICATED` | No session, or the session has expired |
| 403 | `FORBIDDEN` | Wrong role, or another member's data. With `br: "BR-52"`, the module is switched off |
| 404 | `NOT_FOUND` | The record does not exist |
| 409 | `CONFLICT_SLOT` | Another person took that court time first |
| 409 | `HOLD_EXPIRED` | The five-minute hold ran out |
| 409 | `CONFLICT_STATE` | The record is in the wrong state for this action |
| 422 | `BR_VIOLATION` | A named business rule refused the request; `br` carries the rule code |
| 422 | `VALIDATION` | The request is well formed but not acceptable in the current state |
| 429 | `RATE_LIMITED` | Too many attempts in a short time |
### 2. Quality attributes
#### 2.1 Correctness and reliability
Two bookings can never own the same court time, and money never disagrees with the schedule.
| ID | Requirement |
| NFR-01 | No two bookings may own the same court time, under any concurrency. Both booking paths lock the court row, and a database trigger rejects any overlap. |
| NFR-02 | No coach may be scheduled into two overlapping sessions. |
| NFR-03 | A confirmed booking always has its payment and invoice, written in the same transaction. |
| NFR-08 | Any request that takes money or changes a schedule accepts an `Idempotency-Key`. A replay returns the first result and never charges twice. |
| NFR-09 | With no `DATABASE_URL`, the application migrates and seeds an embedded PGLite database, so a fresh copy runs offline. |
| NFR-10 | Losing the assistant's model degrades only the assistant, which falls back to rule-based answers. |
#### 2.2 Performance
The screens staff and members open most often must cost as few database round trips as possible.
| ID | Requirement |
| NFR-04 | `GET /v1/me` issues its independent reads concurrently, so a sign-in costs one round trip rather than seven. |
| NFR-05 | Read-only endpoints open no transaction, which saves two round trips to a remote database. |
| NFR-06 | The front desk badge asks for a count only (`?brief=1`), which runs one aggregate query. |
| NFR-07 | The job loop first checks, in one query, which jobs are due. A pass with nothing due costs one query. |
#### 2.3 Usability
| ID | Requirement |
| NFR-11 | Every screen works at a width of 375 px. |
| NFR-12 | A refusal tells the user what to do instead, as a sentence rather than a code. |
| NFR-13 | Text renders Vietnamese diacritics correctly, and currency is never upper-cased (1,500,000đ, never 1,500,000Đ). |
| NFR-14 | Motion is decorative and never carries meaning on its own. |
#### 2.4 Auditability
| ID | Requirement |
| NFR-15 | Every staff-only change writes an audit row naming the actor, action, record and time. This covers refunds, reconciliation, shift closes, settings, sessions, classes, staff accounts, attendance corrections and payment links. No endpoint deletes an audit row. |
| NFR-16 | Member, payment and invoice codes come from a counter table and have no gaps within each kind. |
#### 2.5 Security and privacy
Authorisation is decided on the server for every request, and member data stays inside the centre.
| ID | Requirement |
| NFR-17 | Passwords are stored only as salted hashes and are never written to logs. |
| NFR-18 | Session tokens are stored as SHA-256 hashes. Member sessions last seven days and staff sessions twelve hours. |
| NFR-19 | Every request is authorised on the server. Hiding a button is not a control. |
| NFR-20 | A member can read only their own bookings, receipts and profile. A read of another member's data returns `403`. |
| NFR-21 | Health notes and guardian details are shown only to those who need them and are never sent to the assistant's model. |
| NFR-22 | In production, one-tap demo sign-in and on-screen codes are off unless `VITE_DEMO_LOGINS` or `OTP_ECHO` is set explicitly. |
| NFR-23 | A switched-off module (F4 training) answers `403` with `BR-52` on every route. |
| NFR-24 | Report exports are built on request from the same queries as the screens, and are not stored. |
| NFR-25 | An online payment is trusted only when read from payOS or carried by a verified webhook signature. |
| NFR-26 | Sign-in locks for 15 minutes after five wrong passwords, and a one-time code after five wrong attempts. |
#### 2.6 Maintainability
The requirements in this document are checked by executable tests, so a change that breaks one fails before release.
- `npm test` runs the unit tests for pricing, refunds, check-in windows and other rules.
- `npm run check:api` drives the real API against a real database and checks the money and schedule rules end to end.
- `npm run typecheck` checks the TypeScript types across the application.

### 3. Common requirements
These requirements apply to every function, so the use cases do not repeat them.
| Area | Requirement |
| Idempotency | Requests that take money or change a schedule accept an `Idempotency-Key`; a replay returns the first result. |
| Audit | Every staff-only change writes an audit row, and no endpoint deletes one. |
| Money | Amounts are whole VND, rounded once to the nearest 1,000đ after discounts. Payments are never deleted; a refund is a new negative payment. |
| Codes | Member, payment and invoice codes have no gaps within each kind. |
| Time | All times are stored with a time zone and shown in Asia/Ho\_Chi\_Minh time. |
| Sessions | Member sessions last seven days and staff sessions twelve hours. |
| Lockout | Five wrong passwords, or five wrong one-time codes, lock that path for 15 minutes. |
| Rate limits | Assistant questions: 800 characters each, 20 a minute. Plan orders: 3 a minute, 10 an hour. |
| Notifications | Notifications are queued and sent in batches of 50, with up to five attempts each. Plan reminders go 7, 3 and 0 days before the end date. |
| Background jobs | The jobs listed in III.1.4 run in one loop every 15 seconds. |
| Language | Every screen is available in English and Vietnamese, and Vietnamese diacritics render correctly. |
| Layout | Every screen works at a width of 375 px. |
